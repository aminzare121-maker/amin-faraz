# برنامه جواب — قرارداد فرمان‌های مالک

نام رسمی: «برنامه جواب» (JAVAB). این سامانه بر مبنای هسته گزارش و دستور GitHub ساخته شده است.
محل اصلی: مخزن aminzare121-maker/amin-faraz، پوشه amin-ai-support/control.

## فرمان آغاز
مالک در گفتگو می‌گوید:
«برنامه جواب را فعال کن. دستور: [شرح کار]. خودکار تا [معیار دقیق نتیجه] ادامه بده.»

واسط اجرایی در همان نوبت، در صورت داشتن دسترسی مجاز:
1. پروژه و معیار پایان را از متن تشخیص می‌دهد، یک Issue تازه با نام «برنامه جواب | عنوان کار» ایجاد می‌کند و شرح هدف و معیار قبولی را در بدنه آن ثبت می‌کند.
2. Issue شماره یکتا دارد؛ در بدنه با قالب JAVAB_TASK_V1 و task_id برابر شماره Issue قرار می‌گیرد.
3. اگر برای ادامه در آینده اجرای دوره‌ای لازم باشد، برای **همان کار** یک Automation مستقل با شناسه Issue و دستور ادامه و ارسال گزارش ایجاد می‌کند. ایجاد خودکار Automation صرفاً با پیاده‌سازی کد GitHub انجام نمی‌شود؛ ChatGPT باید در نوبت فعال‌سازی ابزار مربوط را صدا بزند و موفقیت را تأیید کند.
4. بعد از هر کار واقعی، خلاصه غیرمحرمانه در قالب JAVAB_REPORT_V1 به **همان** Issue ارسال می‌شود. GitHub Actions پس از اعتبارسنجی، پاسخ JAVAB_DIRECTIVE_V1 را در همان Issue ثبت می‌کند.
5. در نوبت اجرایی بعدی، عامل دستور را می‌خواند و ادامه می‌دهد. پاسخ قاعده‌محور است؛ به معنای فعال شدن خودکار ChatGPT در هر لحظه نیست.

نمونه بدنه Issue، پس از اینکه شماره Issue مثلاً 101 شده باشد:

    JAVAB_TASK_V1
    {
      "task_id": 101,
      "project": "support",
      "goal": "ساخت و آزمون موتور پشتیبانی فارسی برای برنامه مشخص",
      "success_criteria": "آزمون عملی پذیرش و ثبت نتیجه با شواهد قابل بازتولید"
    }

نمونه گزارش:

    JAVAB_REPORT_V1
    {
      "task_id": 101,
      "report_id": "task-101-cycle-0001",
      "project": "support",
      "phase": "diagnostics",
      "status": "in_progress",
      "summary": "مستندات واقعی بررسی شدند؛ آزمون مشتری هنوز اجرا نشده است.",
      "goal_met": false
    }

اگر status برابر passed باشد، شناسه commit_sha کامل ۴۰ رقمی و ci_run_id موفق و منطبق لازم است. CI به معنی برآورده شدن هدف مالک نیست. تنها اگر شواهد هدف هم قابل بررسی باشند، پرونده برای تأیید مالک آماده می‌شود؛ ادعای پایانِ خودکار وجود ندارد.

## فرمان توقف
«برنامه جواب متوقف کن» باید توسط عاملِ پاسخ‌دهنده به‌عنوان درخواست توقف همان کار یا کارهای مشخص‌شده اجرا شود. قدم‌های لازم:
- برای هر کار هدف، Issue مربوطه را در GitHub ببندد؛ از آن پس گزارش جدید توسط کنترل‌کننده رد می‌شود.
- اگر Automation مستقلی برای آن کار ایجاد شده، آن را هم متوقف کند و وضعیت توقف را بررسی کند.
- اگر چند کار فعال و نام‌گذاری‌نشده هستند، شناسایی دامنه توقف باید روشن باشد؛ بدون شناخت هدف، کار دیگر را متوقف نکند.
- بستن Issue نمی‌تواند فرایندی را که از قبل روی runner شروع شده با قطعیت فوری متوقف کند. توقف امن اجرای در جریان نیازمند بررسی همان محیط و لغو جداگانه است.

## اجرای موازی و عدم تداخل
- هر Issue یک وظیفه مستقل، با گزارش‌ها و پاسخ‌های خودش است. کلید هم‌زمانی Github Actions شامل شماره Issue و شناسه کامنت است و هیچ قفل مشترک برنامه جواب وجود ندارد.
- در کارهای کدنویسی هم‌زمان، باید برای هر وظیفه شاخه اختصاصی، مسیر فایل و آزمون جدا در نظر گرفت؛ تعارض ادغام به main باید به‌صورت واقعی حل شود. نمی‌توان عدم تداخل را مطلقاً تضمین کرد.
- GitHub Actions ممکن است به سبب محدودیت runner یا سهمیه در صف قرار گیرد. یک Automation نیز ممکن است با محدودیت‌های زمانی اجرا شود؛ **بدون صف بودن مطلق یا اجرای بی‌وقفه تضمین نمی‌شود.**
- ساخت Issue و دریافت دستور از GitHub مدل هوش مصنوعی نیست و خودِ ChatGPT را در محصول داخلی کنترل نمی‌کند. ادامه واقعی پروژه به اجرای عامل در نوبت مجاز یا Automation هر وظیفه نیاز دارد.
- اطلاعات حساس و مکالمات خصوصی به Issue عمومی فرستاده نمی‌شود.

## وضعیت
کد «برنامه جواب» پس از تست واحد و آزمون رفت‌وبرگشت واقعی فقط در حدود قابلیت‌های آزمایش‌شده موفق محسوب می‌شود. نسخه نخست Issue #68 کانال قدیمی واحد است؛ نسخه مستقل جدید از Issueهای متعدد با عنوان «برنامه جواب | ...» استفاده می‌کند.

موارد نیازمند آزمایش مستقل: چند Issue هم‌زمان واقعی، ثبت پاسخ هر کدام، توقف یک Issue بدون اثر روی دیگری، کارکرد Automation جداگانه در چند نوبت، و اصلاح واقعی پروژه تا معیار نهایی.
